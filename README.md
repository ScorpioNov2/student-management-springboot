## Assignment (Лабораторная работа №3. Backend на Java с авторизацией)

## Цель
В рамках лабораторной работы необходимо перенести backend системы управления студентами из лабораторной работы №2 на Java и развить его до полноценного серверного приложения с хранением данных, пользователями и разграничением доступа.

Основная бизнес-логика предыдущей лабораторной работы должна быть сохранена. Приложение по-прежнему должно предоставлять REST API для работы со студентами, однако теперь данные должны храниться в реляционной базе данных, а доступ к операциям должен зависеть от авторизации и роли пользователя.

## Работа со студентами
Необходимо сохранить REST API, разработанный в предыдущей лабораторной работе.

Приложение должно поддерживать получение списка студентов, получение отдельного студента, создание, полное и частичное изменение, а также удаление.

При работе со списком студентов необходимо сохранить возможность поиска, фильтрации, сортировки и пагинации.

Параметры запроса и формат взаимодействия должны быть организованы таким образом, чтобы API оставался удобным для использования клиентским приложением.

Для взаимодействия с базой данных необходимо использовать технологию доступа к данным, указанную преподавателем в варианте задания. В качестве такой технологии могут использоваться Hibernate / JPA, EclipseLink / JPA, jOOQ или другой согласованный инструмент.

## Пользователи и авторизация
В системе необходимо добавить работу с пользователями.

Пользователь должен иметь как минимум уникальное имя, электронную почту, пароль и роль.

Регистрация должна создавать нового пользователя только после проверки корректности введенных данных.

Пароли не должны храниться в открытом виде.

После успешной авторизации пользователь должен получать данные, необходимые для дальнейшего обращения к защищенным ресурсам.

### JWT
Для авторизации необходимо использовать JWT.

Механизм авторизации должен поддерживать access- и refresh-токены и позволять пользователю продолжать работу без повторного ввода логина и пароля при истечении access-токена.

### Роли и разграничение доступа
В системе необходимо предусмотреть как минимум две роли:
*   ADMIN
*   USER

Пользователь с ролью ADMIN должен иметь возможность выполнять все операции со студентами.

Пользователь с ролью USER должен иметь возможность просматривать список студентов и получать информацию об отдельном студенте, но не изменять данные.

Разграничение прав должно выполняться непосредственно на backend.

## Архитектура приложения
Приложение должно иметь понятное разделение ответственности между его частями. Работа с HTTP-запросами, бизнес-логика, доступ к данным и представление данных не должны быть смешаны в одном компоненте.

Для передачи данных через REST API необходимо использовать DTO либо аналогичный подход, отделяющий внешний контракт API от внутренней модели приложения.

Конкретная структура пакетов и классов определяется разработчиком.

## Валидация и обработка ошибок
Необходимо сохранить серверную валидацию, реализованную в предыдущей лабораторной работе, и расширить её с учётом появления пользователей.

Backend должен проверять корректность поступающих данных, ограничения модели и уникальность тех полей, для которых она необходима.

## Конфигурация и логирование
Приложение должно содержать серверное логирование, достаточное для анализа его работы и возникающих ошибок.

Конфигурация, зависящая от окружения, должна быть вынесена за пределы исходного кода.

В проекте необходимо предоставить `.env.example` либо аналогичный пример конфигурации, позволяющий понять, какие параметры требуются для запуска приложения.

### Реализованный backend
Backend находится в `backend/`. Перед запуском скопируйте `backend/.env.example` в `backend/.env` и задайте `JWT_SECRET` случайным секретом длиной не менее 32 байт. Переменные окружения имеют приоритет над значениями из `.env`.

Запуск из PowerShell:

```powershell
Set-Location backend
.\mvnw.cmd spring-boot:run
```

По умолчанию приложение использует SQLite. Для PostgreSQL задайте `DB_URL=jdbc:postgresql://localhost:5432/student_management`, `DB_DRIVER=org.postgresql.Driver`, `JOOQ_SQL_DIALECT=POSTGRES` и `FLYWAY_LOCATIONS=classpath:db/migration-postgresql`.

Основные endpoints:

* `POST /api/auth/register` — регистрация с `username`, `email`, `password` (новые пользователи получают роль `USER`).
* `POST /api/auth/login` — вход с `username` или email и `password`.
* `POST /api/auth/refresh` — ротация refresh token по полю `refreshToken`.
* `GET /api/students` — список и QUERY/search endpoint через query-параметры: `search`, `fullName`, `groupName`, `isuId`, `dormitoryNumber`, `foreigner`, а также `page`, `size`, `sortBy`, `sortDirection`. `page` начинается с 0, `size` допускает значения от 1 до 100.
* `GET /api/students/{id}` — получение студента.
* `POST /api/students`, `PATCH /api/students/{id}`, `DELETE /api/students/{id}` — изменения доступны только `ADMIN`.

Все endpoints студентов требуют `Authorization: Bearer <accessToken>`. Для предоставления роли администратора измените `users.role` на `ADMIN` для доверенной учетной записи непосредственно в БД; публичная регистрация не позволяет назначить эту роль. Ошибки API возвращаются в JSON с полями `timestamp`, `status`, `error`, `message`, `path` и `validationErrors`.

Маршруты для `students` соответствуют CRUD-шаблону `GET /api/{resource}`, `GET /api/{resource}/{id}`, `POST /api/{resource}`, `PATCH /api/{resource}/{id}`, `DELETE /api/{resource}/{id}`. В HTTP нет стандартного метода `QUERY`: поиск и фильтрация выполняются через `GET /api/students` с query-параметрами; ресурс называется `students`, а не `requests`. ISU ID должен быть положительным и уникальным; имя студента не должно содержать цифры; номер общежития должен быть положительным. Нарушение ограничений возвращает единый JSON-ответ с HTTP 400, дубликат ISU ID — HTTP 409, отсутствующий студент — HTTP 404.

Импортируйте `backend/postman/Student-Management.postman_collection.json` в Postman. Выполните `Register USER` и `Refresh USER tokens`. Создайте учетную запись через `Register ADMIN account`, назначьте ей роль в локальной БД, затем выполните `Login ADMIN` и `POST create student` — запрос сохранит `studentId`. После этого запустите запросы USER, чтобы проверить чтение и запреты POST/PATCH/DELETE, а затем запросы ADMIN для PATCH/DELETE:

```sql
UPDATE users SET role = 'ADMIN' WHERE username = '<adminUsername из переменных коллекции>';
```

После этого выполните `Login ADMIN` и запросы в папке `Students - ADMIN`. Измените `uniqueIsuId`, если такой ISU ID уже есть в базе. Swagger UI доступен по `/swagger-ui.html`, OpenAPI JSON — по `/v3/api-docs`.
